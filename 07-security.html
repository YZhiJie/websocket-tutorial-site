第 7 章 WebSocket 安全机制 ​

WebSocket 建立的是一条长期、双向的连接：一旦握手成功，后续消息不再经过 HTTP 的层层检查。 这意味着安全必须在握手前、建连时、每条消息上反复做，而不是"登录过一次就万事大吉"。 本章所有防御手段都有可运行代码（examples/node/secure-server.js）和实测攻击用例。

7.1 威胁模型：先知道敌人怎么攻击 ​

威胁典型手法后果本章防御手段
窃听 / 中间人篡改在公共网络抓明文 ws:// 流量凭证、聊天内容泄露或被改全程 wss://（TLS）
CSWSH 跨站劫持诱导已登录用户打开恶意页面，页面里 JS 直连你的 WebSocket攻击者冒用受害者身份收发消息Origin 白名单 + 不唯 Cookie 论
未授权访问不登录直接连 /ws 拉数据数据泄露握手阶段 Token 鉴权（失败 401）
越权操作连接合法，但发消息操作别人的房间/资源横向越权每条消息做业务级授权
大包内存攻击发送 GB 级消息拖垮服务端内存OOM、服务宕机maxPayload 大小上限

核心原则：纵深防御（Defense in Depth）——任何一道关卡都可能失守，多层独立校验让攻击者必须连续绕过全部防线。

7.2 传输安全：生产环境只用 wss:// ​

wss:// 就是 WebSocket over TLS，与 https:// 共用同一套证书体系和 443 端口：

  • 明文 ws:// 下，握手头部（含 token、cookie）和每条消息在网络上都可以被中间人读取、篡改。
  • 混合内容限制：部署了 HTTPS 的页面里，浏览器禁止连接 ws://，只能用 wss://（本地 localhost 开发时例外）。
  • 常见误解：帧的掩码（Mask）不是加密。客户端掩码只是 XOR 混淆，密钥就在帧头里明文传输，任何人都能解开，它只用于防止恶意字节流欺骗中间代理，与安全无关。
  • 实践：应用服务器继续监听内网明文端口，由 Nginx/网关终止 TLS（配置见第 9 章 Q1），证书可用 Let's Encrypt 免费签发并自动续期。

7.3 CSWSH：跨站 WebSocket 劫持 ​

这是 WebSocket 特有的头号风险，因为浏览器对 WebSocket 不执行同源策略（CORS）：

攻击成立的两个条件：

  1. 用户已登录目标站点，浏览器持有会话 Cookie；
  2. 目标服务端只凭 Cookie 认证，且不校验 Origin。

于是攻击者页面里一行 new WebSocket('wss://app.com') 就会让浏览器自动带上受害者 Cookie 完成连接，攻击者的 JS 可以任意收发消息——注意，跨域虽然限制"读 HTTP 响应"，但 WebSocket 建立后没有这层保护。

防御：握手阶段校验 Origin 白名单。 浏览器发起的 WebSocket 请求必定携带 Origin 头（标明页面来源），ws 库在 verifyClient 里拦截：

javascript
const ALLOWED_ORIGINS = new Set(['http://localhost:5173', 'https://app.example.com']);

const wss = new WebSocketServer({
  port: 8080,
  verifyClient(info) {
    const origin = info.req.headers.origin;
    // 非浏览器客户端可能不带 Origin；浏览器请求带了就必须在白名单内
    if (origin && !ALLOWED_ORIGINS.has(origin)) return false; // → 直接 HTTP 401
    return true;
  },
});

7.4 身份认证：把未登录连接挡在握手阶段 ​

认证信息的三种携带方式：

方式写法优点风险 / 注意
URL Querywss://host/ws?token=xxx最通用，浏览器/工具都支持Token 会进网关访问日志、浏览器历史；必须配 wss，且用短期令牌
Cookie浏览器自动携带无需 JS 处理正是 CSWSH 被利用的点，必须叠加 Origin 校验；注意 SameSite
子协议头new WebSocket(url, ['bearer', token])不进 URL/日志服务端需回 Sec-WebSocket-Protocol 确认，写法略绕

浏览器原生 WebSocket API 无法设置 Authorization 请求头，这是很多人踩的坑； 非要用 Header 认证只能改用 SockJS/Socket.IO 或走子协议/Query 传递。

推荐姿势（握手拒绝，省资源）——在 verifyClient 里一并完成 Origin + Token 校验，失败返回 401，恶意连接根本不进入业务层：

javascript
function verifyClient(info) {
  const { req } = info;
  const origin = req.headers.origin;
  if (origin && !ALLOWED_ORIGINS.has(origin)) return false;

  const requestUrl = new URL(req.url, 'http://localhost'); // WHATWG URL（勿用已弃用的 url.parse）
  const token = requestUrl.searchParams.get('token');
  if (!isValidToken(token)) return false; // 真实项目验 JWT 签名与过期时间
  return true;
}

7.5 授权与输入校验：连接合法 ≠ 每条消息都合法 ​

业务级授权（防越权）：身份通过只代表"你是谁"，每次敏感操作还要检查"你能做什么"：

javascript
ws.on('message', (raw) => {
  const msg = JSON.parse(raw);
  // 例如加入房间：必须核对该用户是否有权进入 roomId，而不是相信客户端上报的任何 roomId
  if (!userCanJoinRoom(ws.userId, msg.roomId)) {
    ws.close(1008, '无权访问该房间');
    return;
  }
});

输入校验（防注入 / 崩溃 / XSS）：

  1. JSON.parse 必须包 try-catch，非法消息回错误提示，绝不让进程崩溃。
  2. 用字段白名单：只接受约定字段，客户端伪造的 role: 'admin'、isOwner: true 等字段直接忽略或拒绝。
  3. 校验类型和长度（如 text 必须是 1~500 字符的字符串）。
  4. XSS 在渲染端防：WebSocket 本身不会执行脚本，危险发生在把消息插入 DOM 时——永远用 textContent，不要 innerHTML 拼接用户内容：
javascript
// ❌ 危险：消息含 <img src=x onerror=alert(1)> 就会在所有客户端执行
logEl.innerHTML += msg.text;
// ✅ 安全：textContent 会把内容当纯文本转义
const p = document.createElement('p');
p.textContent = msg.text;
logEl.appendChild(p);

7.6 限流与资源耗尽防护 ​

长连接服务最容易被三类资源问题打垮，全部要在服务端设防：

javascript
const wss = new WebSocketServer({
  port: 8080,
  maxPayload: 4 * 1024, // ① 单条消息上限 4KB，超出 ws 自动以 1009 关闭连接
  verifyClient,
});

// ② 单 IP 连接数限制：连接建立 +1、关闭 -1，超限以 1013(Try Again Later) 拒绝
// ③ 单连接消息频率：滑动窗口（如 1s 内最多 5 条），超限 1013 关闭

补充要点：

  • 背压（backpressure）：向慢客户端疯狂 send() 会让数据堆积在服务端内存。应检查 ws.bufferedAmount（浏览器端也有同名属性），积压过大时降速或断开。
  • 文件描述符：高并发部署调大 ulimit -n，并在 Nginx/网关层做连接数与速率限制（limit_conn / limit_req）。
  • 广播类服务天然放大攻击流量（一条消息扇给上千人），因此入站频率限制比普通 HTTP API 更严格。

7.8 安全自查清单 ​

上线前逐条核对：

  • [ ] 生产环境全程 wss://，证书自动续期；HTTPS 页面未混用 ws://
  • [ ] 握手校验 Origin 白名单（防 CSWSH）
  • [ ] 握手阶段完成 Token 鉴权，失败返回 401 或立即 close(1008)
  • [ ] 不把长期密钥放 URL query；如使用 query 令牌则确保短时效 + wss
  • [ ] 每条敏感消息做业务级授权（房间/资源级），不信任客户端上报的身份字段
  • [ ] 所有入站消息：JSON try-catch、字段白名单、类型与长度校验
  • [ ] 前端用 textContent 等安全 API 渲染用户内容，杜绝 innerHTML 注入
  • [ ] 配置 maxPayload、单 IP 连接数、消息频率三类限制
  • [ ] 监控 bufferedAmount 防慢客户端拖垮内存
  • [ ] 敏感操作有审计日志；安全相关关闭码（1008/1009/1013）有监控告警

7.9 RFC 6455 协议规范与标准解读 ​

前面的小节讲"怎么做才安全"，这一节回到规范本身：WebSocket 到底由哪份标准定义、哪些安全要求是标准写明的、哪些只是"业界做法"。排错时，"标准怎么规定"往往是多方（浏览器、Nginx、各家语言库）行为不一致时的最终裁判依据。

7.9.1 先分清两份标准：线协议 ≠ 编程 API ​

很多初学者把 WebSocket 当作"一个 API"，实际上它由两份独立标准定义，边界非常关键：

RFC 6455（IETF 标准）WHATWG WebSocket API（Living Standard）
定义什么线协议：握手报文、数据帧字节布局、掩码、关闭码、扩展协商浏览器内编程接口：new WebSocket()、onopen/onmessage/onclose、readyState、bufferedAmount
关注问题字节在 TCP 上长什么样、收发双方状态机JS 代码如何发起连接和收事件
遵循者ws、websockets、Netty、gorilla 等所有服务端/客户端库各浏览器引擎（Chromium/Firefox/Safari）
典型"不归我管"不规定你怎么写业务消息格式不规定服务端怎么校验 Origin，也不让 JS 设 Authorization 头

实践意义：你在 Node 里用 ws 库时，帧解析、掩码、自动回 Pong、Accept 计算都是库按 RFC 6455 实现的；而 7.3~7.7 里的 Origin 策略、Token 鉴权、业务授权、输入校验，协议一条都没替你做——标准明确把它们留给了应用。

7.9.2 规范语言：读懂 MUST / SHOULD / MAY ​

RFC 6455 沿用 RFC 2119 的规范性关键词，读标准时这三个词的力度完全不同：

  • MUST（必须）/ MUST NOT（禁止）：不合规就是协议错误，对端可以直接失败连接。例如"客户端发送的帧必须掩码""控制帧不能分片"。
  • SHOULD（应当）：有合理理由可以不做，但必须理解后果。例如服务端应当校验 Origin。
  • MAY（可以）：可选项。例如连接可以协商扩展。

RFC 6455 正文共 14 节，与工程关系最紧的是：§3 URI（ws/wss）、§4 打开握手、§5 数据帧、§7 关闭与状态码、§9 扩展，以及本章重点的 §10 Security Considerations（完整地图见上图）。

7.9.3 规范摘要里的四个安全事实 ​

RFC 6455 开篇摘要第一句就定义了它的安全模型，建议逐字理解：

协议使"在受控环境中运行不可信代码的客户端"与"明确选择接受该代码通信的远端主机"之间能够双向通信；安全模型是 Web 浏览器通用的基于 Origin（origin-based）的模型。

由此推出四个经常被误解的事实：

  1. 安全模型是"服务端选择加入（opt-in）"。浏览器会自动带上 Origin，但接受还是拒绝完全由服务端决定；不做 Origin 校验等于默认对所有网站 opt-in（见 7.3 的 CSWSH）。
  2. Sec-WebSocket-Key / SHA-1 不是认证、不是加密。握手要求服务端把 Key 拼上魔法 GUID 后取 SHA-1+Base64 返回，只是为了证明对端确实收到并理解了一个 WebSocket 握手，防止普通 HTTP 服务器/缓存中介被误升级。SHA-1 在此不承担任何密码学安全职责（§10.8 专门说明：已有的 SHA-1 碰撞研究不影响 WebSocket 安全）。所以"握手成功了"绝不代表"用户已登录"。
  3. 客户端掩码防的是中介设施，不是防窃听。规范要求浏览器→服务端每个帧必须带随机掩码（§5.3），目的是让攻击者无法构造出在中间代理/缓存看来形如固定 HTTP 请求的字节序列（§10.3 称之为针对基础设施的攻击）。掩码密钥就明文放在帧头，任何中间人都能解开，它不提供机密性。
  4. 机密性与完整性只能靠 TLS。§10.6 明确：需要防窃听/篡改时使用 wss（TLS）。这也是 7.2 反复强调生产环境禁用明文 ws:// 的规范依据。

7.9.4 §10 Security Considerations 逐条解读 ​

RFC 6455 §10 共 8 个小节，下表把每条规范要求映射到本章的具体实践：

规范条款标准的要求/警告本章对应实践
§10.1 非浏览器客户端Origin、只能发特定头等浏览器强制的规则，在 curl/脚本等非浏览器客户端面前全都可以伪造；服务端不能假设对端"是浏览器就守规矩"Origin 只是第一道门，必须再做 Token 鉴权（7.4）；security-test.js 正是用 Node 脚本伪造 Origin 验证
§10.2 Origin 考量浏览器客户端会发送 Origin（定义见 RFC 6454），服务端不希望接受该来源时应拒绝（返回适当 HTTP 错误码）Origin 白名单 + verifyClient 返回 false → 401（7.3）
§10.3 对基础设施的攻击（掩码）强制掩码避免恶意帧被中介误解析为 HTTP 请求，污染缓存或绕过代理；服务端收到未掩码帧 MUST 以 1002 失败连接由 ws 库强制；自己实现裸协议时必须遵守，不可"兼容"未掩码客户端
§10.4 实现相关的限制实现必须设置资源限制：单帧/总消息大小、连接建立速率、总连接数等，防止耗尽内存/CPUmaxPayload: 4KB（超限 1009）、单 IP 3 连接（1013）、滑动窗口限流（1013）（7.7）
§10.5 WebSocket 客户端认证协议本身不定义认证，应复用 Web 层机制：Cookie、HTTP 头、TLS 客户端证书等Query/Cookie/子协议三种载体对比（7.4）；高安全场景可用 TLS 双向认证
§10.6 连接机密性与完整性明文连接上流量可被读取与篡改；需要保密时使用 TLS全站 wss:// + 混合内容限制（7.2）
§10.7 非法数据的处理收到攻击性/不合规数据应直接失败连接，不要尝试"修好"它后继续处理JSON 解析失败的处理策略：消息级非法数据回 error 不断连、协议级违规交给库断连（7.7 第六道防线）
§10.8 握手中的 SHA-1重申 SHA-1 仅用于握手 nonce 证明，非安全用途不要把 Sec-WebSocket-Accept 当成服务端可信凭证

7.9.5 分帧与关闭：库帮你兜住的 MUST 与留给你的约定 ​

下列都是 RFC 6455 的硬性条款（§5/§7/§8），成熟库会自动遵守；自己手写解析器或排查怪异客户端行为时必须知道：

  • RSV1/2/3 位必须为 0，除非经扩展协商赋予含义（如压缩扩展占用 RSV1）；收到非零且未协商的 RSV 位 → 关闭 1002。
  • 掩码方向是单向的：客户端→服务端必须掩码，服务端→客户端必须不掩码；反向违规都应关闭 1002。
  • 控制帧（Close/Ping/Pong，opcode 8/9/A）载荷 ≤ 125 字节且禁止分片；Ping 必须回复 Pong 并原样带回载荷（ws 库自动完成）。
  • 分片规则：一条消息首帧 opcode=1/2，后续帧 opcode=0，最后一帧 FIN=1；控制帧允许插入分片消息中间。
  • 文本帧必须是合法 UTF-8，服务端收到非法编码 → 关闭 1007（§8.1），二进制帧不做此限制。
  • 关闭是双向握手：发出或收到 Close 帧后，应回发 Close 再关闭 TCP；Close 载荷前 2 字节是状态码，后面是 UTF-8 文本原因。
  • 关闭码分段（§7.4）：
范围含义使用规则
1000–1015规范定义（1000 正常、1001 离开、1008 策略拒绝、1009 消息过大、1013 临时无法处理…）1004 保留；1005/1006/1015 是 API 层哨兵值，永不出现在线上帧里
3000–3999私有/多方约定先到先得，可向 IANA 注册（§11.7）
4000–4999纯私有不可注册，团队内部约定即可

本章安全服务器使用的 1008/1009/1013 全部取自规范段；自定义"Token 过期""设备数超限"等业务语义，应从 4000+ 段选码。

7.9.6 演进中的标准：压缩扩展与 HTTP/2 带来的新攻击面 ​

核心协议之外，还要知道三份直接影响部署与安全的标准：

  • RFC 7692（2015）permessage-deflate 压缩扩展。握手通过 Sec-WebSocket-Extensions: permessage-deflate 协商，对高重复小消息收益明显，但它带来 BREACH/CRIME 同族的压缩侧信道：在 TLS 上压缩"秘密（如 Token、CSRF 值）+ 攻击者可部分影响的内容"时，攻击者可通过密文长度变化逐字节推断秘密。因此：敏感频道可在 ws 服务端关闭压缩（perMessageDeflate: false），或确保秘密不与用户可控内容进入同一压缩上下文。注意 ws 库默认开启该扩展，这不是免费的午餐。
  • RFC 8441（2018）基于 HTTP/2 的 WebSocket 引导。在 H2 上不再有 Upgrade: websocket + 101，而是用扩展 CONNECT（:method: CONNECT、:protocol: websocket）在流上建立连接。排查问题时要知道：H2 抓包里看不到经典握手；且 Nginx/网关必须显式支持 RFC 8441 才能代理，否则表现为握手失败。
  • 配套基础标准：Origin 的定义在 RFC 6454（Web Origin Concept，注意区分 scheme+host+port）；反向代理后获取真实 IP 应参考 RFC 7239（Forwarded 头），7.6 的"单 IP 连接数"限流若直接取 TCP 对端地址，在 CDN 后会把全平台限成同一个 IP，必须信任并解析代理头。
  • 浏览器 API 侧，现行标准是 WHATWG 维护的 Living Standard（旧的 W3C 快照已停止维护），查行为兼容性以 WHATWG 与 MDN 为准。

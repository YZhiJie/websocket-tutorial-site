2.2 握手过程详解（附真实抓包） ​

WebSocket 握手复用 HTTP 协议完成——这是它与 HTTP 最紧密的联系。客户端发送一个带有特殊头部的 HTTP GET 请求，要求"升级"协议。

以下是用 curl 模拟握手、抓取本教程配套 echo-server.js 的真实报文：

bash
curl -v -N \
  -H "Connection: Upgrade" \
  -H "Upgrade: websocket" \
  -H "Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==" \
  -H "Sec-WebSocket-Version: 13" \
  -H "Origin: http://localhost" \
  http://localhost:8080

逐行解读：

请求头部（客户端 → 服务端）：

头部作用
Connection: Upgrade告诉服务器：我想升级当前连接为其他协议
Upgrade: websocket指定要升级到的协议名是 websocket
Sec-WebSocket-Key客户端生成的 16 字节随机数的 Base64，用于握手校验（防止缓存代理误认）
Sec-WebSocket-Version: 13协议版本号，当前 RFC 6455 定义的唯一版本是 13
Origin来源标识，服务端可据此做跨域校验

响应头部（服务端 → 客户端）：

头部作用
101 Switching Protocols状态码 101：同意切换协议。此后这个 TCP 连接不再说 HTTP
Sec-WebSocket-Accept服务端把客户端的 Key 拼接固定 GUID 后做 SHA-1 + Base64 的结果，客户端校验它确认对方真的懂 WebSocket

Sec-WebSocket-Accept 的计算公式（了解即可，所有库都会自动处理）：

Sec-WebSocket-Accept = Base64( SHA1( Sec-WebSocket-Key + "258EAFA5-E914-47DA-95CA-C5AB0DC85B11" ) )
1

验证：上面抓包中的 Key dGhlIHNhbXBsZSBub25jZQ== 经计算得到的 Accept 正是 s3pPLMBiTxaQ9kYGzzhZRbK+xOo= —— 这就是 RFC 6455 官方文档里的经典示例值。

握手成功后，这个 TCP 连接就"变身"为 WebSocket 通道，双方开始收发帧（Frame）。

2.3 帧结构 ​

WebSocket 传输的基本单位是帧。一个消息可以由一个或多个帧组成。帧的头部极小：

关键字段：

  • FIN (1 bit)：是否为消息的最后一个帧（消息可拆分成多个帧发送）。
  • opcode (4 bit)：帧类型，这是最重要的字段：
    • 0x0 续帧（消息分片的后续部分）
    • 0x1 文本帧（载荷必须是 UTF-8）
    • 0x2 二进制帧
    • 0x8 关闭帧（Close）
    • 0x9 Ping 帧
    • 0xA Pong 帧
  • Mask (1 bit)：客户端发往服务端的帧必须掩码（XOR 混淆），防止恶意构造的字节流欺骗中间代理；服务端发往客户端的帧不掩码。
  • Payload len：载荷长度。≤125 直接表示；126 表示后跟 2 字节长度；127 表示后跟 8 字节长度（最大约 16EB）。

初学者要点：日常开发几乎不需要手动拼帧——所有语言的 WebSocket 库（ws、websockets、浏览器原生 API）都会自动处理帧的封装、分片重组和掩码。理解帧结构的价值在于排查问题（比如看到 opcode 0x9 就知道是 Ping）。

2.4 关闭连接与状态码 ​

WebSocket 的关闭是"礼貌的握手"：任一方发送 Close 帧（可携带状态码和原因字符串），另一方回一个 Close 帧，然后断开 TCP。

常见状态码（完整表见附录 A）：

状态码含义
1000正常关闭（任务完成）
1001端点离开（如浏览器页面关闭/跳转）
1006异常断开（不会出现在 Close 帧里，仅用于本地表示网络异常掉线）
1008违反策略（如鉴权失败）
1011服务端内部错误

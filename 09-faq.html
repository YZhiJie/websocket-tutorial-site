第 9 章 常见问题与解决方案（FAQ） ​

Q1：连接几分钟没消息就断开了，怎么办？ ​

原因：中间链路（Nginx、云负载均衡、公司代理）会回收空闲 TCP 连接，典型空闲超时 60s。

方案：

  1. 应用内实现心跳（见第 6.1 节），心跳间隔务必小于中间件空闲超时（建议 ≤30s）。
  2. Nginx 反向代理配置示例：
nginx
location /ws {
    proxy_pass http://backend;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;      # 必须：传递 Upgrade 头
    proxy_set_header Connection "upgrade";       # 必须：传递 Connection 头
    proxy_read_timeout 3600s;                    # 调大空闲超时（默认 60s）
}

Q2：为什么收不到对方断开的通知（半开连接）？ ​

TCP 设计上，对端断电/断网时本地不会有任何事件——发送缓冲区还有数据时才会在重传超时后报错。唯一可靠的检测手段就是应用自己定期发心跳。这是 WebSocket 开发最经典的问题。

Q3：消息发送失败/丢失怎么办？ ​

WebSocket 基于 TCP，单条消息内不丢、不乱序，但不保证：

  • 发送时连接恰好断开 → send() 静默失败或抛异常
  • 重连期间的消息 → 完全丢失

方案：应用层 ACK 机制——每条消息带唯一 clientId，服务端收到后回执；客户端超时未收到回执则重发（服务端用 clientId 幂等去重）。

Q4：浏览器控制台报 WebSocket connection failed 怎么排查？ ​

按顺序检查：

  1. 服务端是否启动、端口是否正确（lsof -i :8080）
  2. ws:// 与 wss:// 是否用错——HTTPS 页面只能连 wss://（混合内容限制）
  3. 经过 Nginx/网关时，Upgrade 头是否正确透传（见 Q1 配置）
  4. 跨域问题：WebSocket 不受 CORS 限制，但服务端应校验 Origin 头防 CSWSH 攻击

Q5：并发连接数上不去？ ​

  • 文件描述符限制：ulimit -n 调大（生产建议 65535+）
  • Node.js 单进程内存：每个连接约 10~20KB，10 万连接约 2GB
  • 垂直扩展有限时，用 Redis Pub/Sub 做多进程/多机的消息广播总线

Q6：JSON 太慢/太大？ ​

文本 JSON 适合大多数场景；真正遇到瓶颈时：

  • 二进制序列化：MessagePack / Protobuf（体积减 30~70%，CPU 减半）
  • 高频小消息合并成批次发送（牺牲数 ms 延迟换吞吐）

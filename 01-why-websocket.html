第 1 章 为什么需要 WebSocket ​

1.1 HTTP 的天然局限 ​

HTTP 协议是**请求-响应（Request-Response）**模型：客户端发起请求，服务端返回响应，然后连接结束（或复用给下一个请求）。这个模型有一个根本性限制——服务端永远无法主动联系客户端。

想象一个聊天室场景：小李发了一条消息，服务端收到了，但小王的浏览器对此一无所知。小王要看到这条消息，只能自己再去问一次服务器："有新消息吗？"

1.2 WebSocket 出现之前的"土办法" ​

方案原理延迟资源浪费适用性
短轮询（Polling）客户端每隔 N 秒发一次 HTTP 请求询问高（平均 N/2 秒）极高，大量空响应已淘汰
长轮询（Long Polling）请求挂起，有数据才返回，返回后立刻再发中高，反复建立请求兼容兜底
SSE（Server-Sent Events）HTTP 长连接，服务端可持续推送文本流低低仅服务端→客户端单向
WebSocket真正的全双工长连接，双方随时互发极低极低双向实时场景首选

1.3 WebSocket 是什么 ​

WebSocket 是 HTML5 标准的一部分（协议规范见 RFC 6455，2011 年发布），它在单个 TCP 连接上提供**全双工（full-duplex）**通信通道：

  • 全双工：连接建立后，客户端和服务端可以随时互相发送数据，不需要等待对方请求。
  • 低开销：握手完成后，数据帧头部最小只有 2 字节（对比 HTTP 每次请求几百字节的头部）。
  • 低延迟：消息即时送达，没有轮询间隔。
  • 持久连接：一次握手，长期复用，直到一方主动关闭。

一句话总结：WebSocket 让浏览器和服务器之间拥有了一条类似"打电话"的通道，而 HTTP 更像"发短信"。
